# インストールと使い方 · 0.4.0

Codex Quota Guard は、利用枠の照会と参考情報としての監視を提供します。Python 3.10 以上、POSIX 環境（Linux/macOS）、インストール済みの公式 Codex CLI が必要です。利用条件を満たすアカウントで、通常の認証を完了しておいてください。実行時の依存関係は Python 標準ライブラリのみです。信頼できる PATH 上の公式実行ファイルを使用します。

## インストール

```sh
codex plugin marketplace add knight-bo/codex-quota-guard
```

デスクトップアプリを再起動し、Codex Quota Guard Local を選んでインストールし、有効にします。デスクトップ専用のプラグインで、GitHub からダウンロードして配布されます。GitHub での公開は、公開プラグインディレクトリの承認を意味しません。インストールだけでは監視や調査タスクは始まらず、自動起動や定期実行も設定されません。

## 照会と開始

自然言語では、「Codex の利用枠の残量を確認して」「このタスクを監視して。残量 80% を目標にして、近づいたら一時停止するか先に聞いて。30 秒ごとに確認して」「利用枠の監視を停止して」と依頼できます。一度だけの照会で継続監視が始まることはありません。残しておきたい量を伝えるだけでも、監視開始の依頼にはなりません。

以下はプラグインのルートで実行します。STATE は、リポジトリとプラグインキャッシュの外にある同じ非公開の状態ディレクトリの絶対パスに置き換えてください。現在のユーザーが所有し、権限は 0700、親ディレクトリは信頼できて書き込み可能である必要があります。TASK は、ホストが確認済みの具体的なタスクを指す安定した識別子です。対象が曖昧なら先に確認し、識別子を作り上げないでください。パスワードやトークンなどの秘密情報を含めてはいけません。保存状態と出力には元の識別子ではなくハッシュ化した紐付け情報だけが残ります。この紐付けはタスクを操作する権限を与えません。

手動の照会は日本語テキストで表示します。ホストの監督下で動かす監視には、状態とイベントを読み取れる既定の JSON 出力を使います。

```sh
python3 scripts/quota_guard.py read --bucket codex --state-dir STATE --format text --locale ja
python3 scripts/quota_guard.py start --bucket codex --target 80 --task-key TASK --warn-margin 2 --confirm-margin 1 --interval 30 --state-dir STATE
```

監視は明示的な依頼でのみ開始します。start は watch の別名で、フォアグラウンドで動作し、常駐サービスにはなりません。継続監視を始めるには、ホストが監督付きのバックグラウンドセッションを維持し、セッションハンドルを保存して JSON イベントを読み取りながら、ユーザーの返答も受け付けられる必要があります。両立できなければ、その制限を説明して一度だけ照会してください。継続監視が動いていると伝えてはいけません。nohup、隠れた常駐プロセス、自動起動設定でこの条件を回避しないでください。

## 残量の目標と判定のタイミング

--target には 0 から 100 までの任意の有限値を指定できます。両端と 37.5 のような小数も含みます。使用済みの割合ではなく残量の割合であり、決められた候補から選ぶ方式でもありません。上の例では、既定の警告マージン 2 ポイント、確認マージン 1 ポイントにより、次のようになります。

- 残量が 82% 以下：warning イベントを出力します。
- 残量が 81% 以下：confirmation_required を出力し、ホストが「残量が 80% になったら、このタスクを一時停止しますか？」と確認します。
- 残量が 80% 以下：target_reached を出力し、allow_new_work=false、理由 confirmation_target_reached として新しい作業の受け入れを拒否します。これは連携側が守るべき判定であり、実際にタスクを一時停止したことにはなりません。

適用される期間のどれかが条件を満たすと判定されます。マージンの単位はパーセントポイントで、警告マージンは確認マージン以上、各判定ラインの上限は 100% です。マージンは目標そのものを変えません。初回の有効な測定ですでに目標以下なら、「すでに残量が 80% 以下です。このタスクを今、一時停止しますか？」と直ちに確認します。すでに到達した条件を今後の出来事として扱わないでください。目標が 100 なら残量 100% でも直ちに確認が必要です。目標 0 は利用枠を使い切らない保証にはなりません。一度に複数の段階へ進んだ場合は、質問をまとめて重複を避けます。

目標モードに --reserve、--threshold、--buffer を併用すると拒否されます。以前の「確保量 10%、バッファ 2 ポイント、残量 12% で新しい作業を拒否」という例は互換用の確保量モードだけの説明です。10% 未満を含め、選択した目標を置き換えるものではありません。目標モードの受け入れ判定ラインは目標値そのもので、バッファは 0 です。

## イベント、確認、実際の操作

CLI のイベントは、ユーザーへの通知、通知の到達、許可の取得、実際の一時停止を証明しません。ホストは実際に質問し、返答を別途記録し、操作前に対象タスクの所有関係とサポートされた操作経路を確認する必要があります。無返答は同意ではありません。操作経路がなければ制約を説明してユーザーに手動操作を依頼し、任意のプロセスを終了したりクラウドタスクを停止したりしないでください。--target と --allow-interrupt は併用できません。

既定の JSON の confirmation 段階と events はホストの判断材料です。pause_authorized と task_paused は false のままです。イベントは最大 1 回だけ保存され、通知の到達は保証されません。再起動やイベントの読み逃しがあれば、現在の段階と実際の会話履歴を照合して未実施の確認を行います。新しいイベントがないことを同意の証拠にしてはいけません。

具体的なタスクに対する明示的な許可と確認済みの操作経路がある場合に限り、ホストは許可された操作を実行できます。実際の状態を観測してから一時停止したと報告します。従来の管理対象の中断は、オーケストレーターが所有し、現在の app-server からアクセスできる正確な thread/turn の組に限定されます。確認の省略手段にはならず、再開可能な一時停止も保証しません。チェックポイントは unconfirmed のままです。RPC による中断要求の受理は、タスク完了、保存成功、切り離されたすべてのワーカーの終了を証明しません。

## 停止、再起動、測定の限界

別の端末で同じ STATE を指定して停止します。

```sh
python3 scripts/quota_guard.py stop --state-dir STATE --format text --locale ja
```

元のセッションでプロセスの終了を確認してください。停止要求だけでは終了の証明になりません。Ctrl-C でも停止できます。監視の停止は、監視対象タスクの停止ではありません。目標や監視設定を変更するには新たな明示的な合意が必要で、元の監視の終了を確認してから新しい設定で開始します。

目標到達による受け入れ拒否は、残量の増加、リセット、同じタスクと目標での再起動を経ても保持されます。これらによって作業が自動再開されることはありません。--new-cycle は、ユーザーが新しい監視サイクルを明示的に依頼し、元の監視が停止した後にだけ使います。状態をクリアしても、一時停止や再開の許可、実際の再開を意味しません。

ポーリング、報告の遅延、再試行、他のクライアントによる同時利用により、検出時には目標を下回る可能性があります。目標ぴったりで止まる保証はありません。各期間と観測日時を確認してください。キャッシュ、期限切れ、欠落、模擬、無効な測定値は現在の残量ではなく、目標到達や条件解除の証拠にもなりません。リセット時刻を過ぎても有効な再取得が必要です。codex は明示的に選ぶ区分であり、すべてのモデルに共通ではありません。

接続できない場合は通常の承認・ログイン手順を使用してください。権限、認証、CODEX_HOME の変更による制限回避や、認証情報ファイル・セッションログの直接読み取りは行わないでください。監視は利用枠の購入や新たなタスク操作権限の付与も行いません。
