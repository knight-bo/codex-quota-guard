# 설치 및 사용 안내 · 0.5.0

Codex Quota Guard는 사용 한도를 조회하고 참고용으로 모니터링합니다. Python 3.10 이상, POSIX 환경(Linux/macOS), 설치된 공식 Codex CLI가 필요합니다. 이용 조건에 맞는 계정으로 일반 인증 절차를 완료해야 합니다. 실행 시에는 Python 표준 라이브러리만 사용합니다. 신뢰할 수 있는 PATH에 있는 공식 실행 파일을 사용하세요.

## 설치

```sh
codex plugin marketplace add knight-bo/codex-quota-guard
```

데스크톱 앱을 다시 시작하고 Codex Quota Guard Local을 선택해 설치한 다음 활성화하세요. 데스크톱 전용 플러그인이며 GitHub 다운로드로 배포됩니다. GitHub 공개는 공개 플러그인 디렉터리의 승인을 의미하지 않습니다. 설치만으로 모니터링이나 조사 작업이 시작되지 않으며 자동 시작이나 정기 실행도 설정되지 않습니다.

## 조회 및 시작

자연어로 “Codex 잔여 한도를 확인해 줘”, “이 작업을 모니터링해 줘. 잔여량 80%를 목표로 하고, 가까워지면 일시 중지할지 먼저 물어봐 줘. 30초마다 확인해 줘”, “한도 모니터링을 중지해 줘”라고 요청할 수 있습니다. 일회성 조회는 지속적인 모니터링을 시작하지 않습니다. 남겨 둘 한도를 말하는 것만으로 모니터링 시작을 요청한 것으로 보지도 않습니다.

아래 명령은 플러그인 루트에서 실행하세요. STATE를 동일한 비공개 상태 디렉터리의 절대 경로로 바꾸세요. 이 디렉터리는 저장소와 플러그인 캐시 밖에 있어야 하며, 현재 사용자 소유이고 권한은 0700이어야 합니다. 상위 디렉터리도 신뢰할 수 있고 쓰기 가능해야 합니다. TASK에는 호스트가 확인한 구체적인 작업의 안정적인 식별자를 넣으세요. 대상이 모호하면 먼저 확인하고 식별자를 지어내지 마세요. 비밀번호, 토큰 등 비밀 정보는 넣지 마세요. 저장 상태와 출력에는 원래 식별자 대신 해시로 만든 연결 정보만 남습니다. 이 연결 정보는 작업 제어 권한을 부여하지 않습니다.

수동 조회에는 한국어 텍스트를 사용합니다. 호스트가 감독하는 모니터링은 상태와 이벤트를 읽을 수 있도록 기본 JSON 출력을 사용합니다.

```sh
python3 scripts/quota_guard.py read --bucket codex --state-dir STATE --format text --locale ko
python3 scripts/quota_guard.py start --bucket codex --target 80 --task-key TASK --warn-margin 2 --confirm-margin 1 --interval 30 --state-dir STATE
```

모니터링은 명시적으로 요청한 경우에만 시작합니다. start는 watch의 별칭이며 포그라운드에서 실행되고 백그라운드 서비스가 아닙니다. 지속적인 모니터링을 시작하려면 호스트가 감독 가능한 백그라운드 세션을 유지하고, 세션 핸들을 보관하며, JSON 이벤트를 읽는 동안에도 사용자 답변을 받을 수 있어야 합니다. 이를 함께 유지할 수 없다면 제한을 설명하고 일회성 조회만 하세요. 지속적인 모니터링이 실행 중이라고 말하면 안 됩니다. nohup, 숨겨진 데몬, 자동 시작 설정으로 이 조건을 우회하지 마세요.

## 잔여량 목표와 단계별 조건

--target은 양 끝을 포함해 0부터 100까지의 모든 유한한 값을 받으며 37.5 같은 소수도 지원합니다. 사용한 비율이 아니라 남은 비율이며, 미리 정한 몇 가지 값으로 제한되지 않습니다. 위 예시는 기본 경고 여유값 2%포인트와 확인 여유값 1%포인트를 사용합니다.

- 잔여량 ≤ 82%: warning 이벤트를 출력합니다.
- 잔여량 ≤ 81%: confirmation_required 이벤트를 출력합니다. 호스트는 “잔여량이 80%가 되면 이 작업을 일시 중지할까요?”라고 물어야 합니다.
- 잔여량 ≤ 80%: target_reached 이벤트를 출력하고 allow_new_work=false, 사유 confirmation_target_reached로 새 작업의 시작을 허용하지 않습니다. 이는 연동하는 쪽에서 따라야 하는 허용 여부 판정이며, 작업이 실제로 일시 중지되었다는 뜻은 아닙니다.

적용되는 기간 중 하나라도 조건을 충족하면 해당 단계로 판단합니다. 여유값의 단위는 %포인트이며 경고 여유값은 확인 여유값 이상이어야 하고 각 발동 기준의 상한은 100%입니다. 여유값은 목표 자체를 바꾸지 않습니다. 첫 유효 조회부터 이미 목표 이하라면 “이미 잔여량이 80% 이하입니다. 지금 이 작업을 일시 중지할까요?”라고 즉시 물어야 합니다. 이미 지난 기준을 앞으로 도달할 조건처럼 설명하지 마세요. 목표가 100이면 잔여량이 100%여도 즉시 확인이 필요합니다. 목표 0은 한도 소진을 막는다는 보장이 아닙니다. 한 번의 조회에서 여러 단계가 함께 발생하면 질문을 합쳐 중복을 피하세요.

목표 모드에는 --reserve, --threshold, --buffer를 함께 사용할 수 없으며 해당 조합은 거부됩니다. 이전의 “예비량 10%, 여유분 2%포인트, 잔여량 12%에서 새 작업 거부” 예시는 호환용 예비량 모드에만 해당합니다. 10% 미만의 목표를 포함해 사용자가 선택한 목표를 대신하지 않습니다. 목표 모드의 새 작업 허용 기준은 정확히 목표값이며 버퍼는 0입니다.

## 이벤트, 확인 및 실제 작업 제어

CLI 이벤트는 사용자에게 알림이 전달되었거나, 사용자가 승인했거나, 작업이 실제로 일시 중지되었음을 증명하지 않습니다. 호스트는 실제로 질문하고 답변을 별도로 기록해야 하며, 동작 전에 해당 작업의 소유 관계와 지원되는 제어 경로를 확인해야 합니다. 응답이 없다고 승인한 것은 아닙니다. 지원되는 경로가 없다면 이유를 설명하고 사용자에게 직접 조작을 요청하세요. 임의로 프로세스를 종료하거나 클라우드 작업을 중지해서는 안 됩니다. --target과 --allow-interrupt는 함께 사용할 수 없습니다.

기본 JSON의 confirmation 단계와 events는 호스트가 판단할 때 사용하는 정보입니다. pause_authorized와 task_paused는 false로 유지됩니다. 이벤트는 최대 한 번 저장되며 알림 전달을 보장하지 않습니다. 재시작하거나 이벤트를 놓쳤다면 현재 단계와 실제 대화 기록을 대조해 아직 하지 않은 질문을 해야 합니다. 새 이벤트가 없다는 이유로 승인을 받았다고 판단하지 마세요.

호스트는 해당 작업에 대한 명시적 승인과 확인된 제어 경로가 있을 때만 승인된 동작을 수행할 수 있습니다. 작업의 실제 상태를 관찰한 뒤 일시 중지되었다고 보고해야 합니다. 기존 관리 대상 중단 기능은 오케스트레이터가 소유하고 현재 app-server에서 접근할 수 있는 정확한 thread/turn 쌍으로 제한됩니다. 확인 절차를 생략하는 수단이 아니며 재개 가능한 일시 중지도 보장하지 않습니다. 체크포인트 상태는 unconfirmed입니다. RPC 중단 요청의 수락은 작업 완료, 체크포인트 저장 성공, 분리된 모든 작업 프로세스의 종료를 증명하지 않습니다.

## 중지, 재시작 및 조회의 한계

다른 터미널에서 같은 STATE를 사용해 중지를 요청합니다.

```sh
python3 scripts/quota_guard.py stop --state-dir STATE --format text --locale ko
```

원래 세션에서 프로세스가 실제로 종료되었는지 확인하세요. 중지 요청 자체는 종료를 증명하지 않습니다. 포그라운드에서 Ctrl-C로 중지할 수도 있습니다. 모니터링 중지는 감시하던 작업의 중지가 아닙니다. 목표나 모니터링 설정을 바꾸려면 새로 명시적 합의를 하고, 기존 모니터가 종료된 것을 확인한 뒤 새 설정으로 시작해야 합니다.

목표 도달에 따른 새 작업 차단은 잔여량 증가, 한도 초기화, 같은 작업과 목표를 사용하는 재시작 후에도 유지됩니다. 이러한 변화로 작업이 자동 재개되지는 않습니다. --new-cycle은 사용자가 새 모니터링 주기를 명시적으로 요청하고 기존 모니터가 중지된 뒤에만 사용하세요. 주기 상태를 지우는 것은 작업 일시 중지나 재개를 승인한 것이 아니며 작업이 재개되었다는 증거도 아닙니다.

폴링, 보고 지연, 재시도, 다른 클라이언트의 동시 사용 때문에 감지 시점에는 목표 아래로 내려가 있을 수 있습니다. 정확히 목표에서 멈춘다는 보장은 없습니다. 각 기간과 관측 시각을 따로 확인하세요. 캐시되거나 만료된 값, 누락되거나 모의 생성된 값, 잘못된 값은 현재 잔여량으로 간주할 수 없으며 목표 도달이나 조건 해제를 증명하지도 않습니다. 초기화 시각이 지나도 새로 유효한 조회를 해야 합니다. codex는 명시적으로 선택한 한도 구분이며 모든 모델에 공통으로 적용되는 것은 아닙니다.

접근에 실패하면 일반 승인 또는 로그인 절차를 이용하세요. 권한, 인증 설정, CODEX_HOME을 변경해 제한을 우회하지 마세요. 자격 증명 파일이나 세션 로그를 직접 읽어서 한도를 확인하지 마세요. 모니터링은 한도를 구매하거나 추가 작업 제어 권한을 부여하지 않습니다.

## 선택적인 Tibo 공개 초기화 공지

“Tibo의 공개 초기화 공지를 매시간 감시해 줘”, “Asia/Shanghai에서 completed와 banked만 알려 줘”, “공개 공지를 한 번 확인해 줘”, “공개 초기화 알림을 중지해 줘”라고 요청할 수 있습니다. 별도 `resetwatch`를 사용합니다. 질문은 한 번의 `read`이며 명시적인 감시 요청에만 시작합니다. 호스트는 포그라운드 프로세스를 감독하고 JSON을 읽어 기존 로컬 알림 어댑터에 연결해야 합니다. 알림 경로가 없다면 텍스트/JSON만 가능하다고 설명해야 합니다. 설치만으로 시작하지 않습니다.

`planned`는 계획이며 완료가 아닙니다. `completed`는 제삼자가 기록한 완료 공지, `banked`는 개인 수령과 수동 사용이 확인되지 않은 저장형 초기화, `manual_credit`는 원문 조건을 확인해야 하는 수동 크레딧 공지입니다. 공개 기록은 개인 한도 회복을 증명하지 않으며 크레딧 사용이나 연구의 자동 재개/일시 중지를 하지 않습니다. 제공자의 “직접 검증” 표기도 제공자의 주장일 뿐 독립 확인이나 공식 API가 아닙니다.

PUBLIC_STATE를 저장소/캐시 밖의 비공개 절대 상위 경로로 바꾸세요. 별도 `PUBLIC_STATE/public-reset-watch`, 잠금과 중지 토큰을 사용하며 한도 상태를 바꾸지 않습니다. 첫 조회 성공은 알림 없이 기준선만 만듭니다. 과거 글, 중복, 재시작, 순서가 뒤바뀐 이전 상태는 다시 알리지 않습니다. planned→completed 갱신은 새 상태만 알릴 수 있습니다. 필터를 바꿔도 과거를 재생하지 않습니다. 설정 변경은 중지와 원래 프로세스 종료 확인 후 재시작하세요. 이 감시의 중지는 연구나 한도 감시를 중지하지 않습니다.

`--events`는 planned,completed,banked,manual_credit를 선택하며 기본은 모두입니다. `--interval`은 3600..86400초, 기본 3600입니다. 대기 시간은 재시작 후에도 유지되고 오류 시 재시도 지연은 최대 24시간입니다. `--max-age`는 캐시된 조회/확인 증거의 최대 경과 시간(기본 172800초, 간격 이상 604800 이하), `--event-age`는 새 게시물의 최대 경과 시간(기본 604800, 범위 3600..2592000)입니다. 전체 `--timeout`은 1..30초(기본 10)이며 소켓 시간 제한이 최대 한 번 더 걸릴 수 있습니다. `--timezone`은 설치된 IANA 이름이며 기본 UTC입니다. 기계용 날짜는 UTC를 유지합니다. `--locale`은 기존 대체 규칙을 따르며 JSON 필드와 값은 번역하지 않습니다.

기본 `--provider modelyard`는 고정 공개 RSS `/feed.xml`만 읽습니다. HTML 어댑터와 임의 `--provider-url`은 제거했으며 출처 교체는 코드 검토가 필요합니다. RSS 분류는 제삼자 보고이며 공식 검증이 아닙니다. `fetched_at`은 로컬 조회 증거이고 lastBuildDate/최신 게시 시각은 동기화 증거가 아닙니다. 오래돼도 정상인 feed는 기준선을 만들 수 있으나 범위는 알 수 없습니다. 제품 범위는 제공된 원문을 따르며 불명확하면 알 수 없음으로 표시합니다. 제목/문맥은 제공자의 주장입니다. ChatGPT만 해당하는 기록은 Codex/Work 알림으로 보내지 않습니다. 같은 글의 분류 변경은 `first_observed_status_at`에 따른 로컬 집계 상태 갱신이며 원문 수정 시각을 만들지 않습니다. Callback은 호스트의 기존 로컬 알림 경로용이며 실제 전달은 미검증입니다. 본 환경의 네트워크/Library 다운로드는 차단됐고 직접 제공된 실제 첫 항목 발췌를 테스트했습니다. Robots는 재배포 허가가 아니며 출처 검토를 참조하세요.
